Мы принимаем вклад в Django-GC. Это руководство описывает локальный
процесс разработки, тестов и документации.

Если неясно, подходит ли изменение проекту, сначала откройте issue или draft
pull request.

Держите изменения сфокусированными и добавляйте тесты, когда меняется поведение.

## Настройка окружения

Проект использует `uv` для Python-зависимостей. Установка — в
[документации uv](https://docs.astral.sh/uv/getting-started/installation/).

После клонирования репозитория установите зависимости:

```bash
uv sync --locked --group dev
```

## Линтинг

Ruff читает `ruff.toml`: длина строки 120, список ignore проекта и
`force-exclude` для миграций и Markdown. Не запускайте Ruff без этого
файла — дефолты конфликтуют с атрибутами Django admin и примерами в доках.

```bash
uv run ruff check --config ruff.toml .
uv run pyrefly check
```

Используйте Ruff в pre-commit для линтинга. Опускайте необязательные завершающие
запятые в импортах, коллекциях, вызовах и сигнатурах. Пишите каждое имя
в непустом `__all__` на отдельной строке и сохраняйте порядок экспортов.

## Тесты

```bash
bash .github/scripts/compile-translations.sh
uv run --locked pytest
```

## Документация

Документация собирается [Docusaurus](https://docusaurus.io/). Сайт двуязычный
(английский источник, русские зеркала) и **не** версионируется.
Публичный API помечается бейджами `<Since v="x.y.z" />`.

```bash
cd docs
npm install --global "$(node -p 'require("./package.json").packageManager')"
npm ci
npm run docs:dev
```

Английский — локаль по умолчанию на `/`, без префикса `/en/`. Русский — i18n
overlay на `/ru/`. `docs:dev` поднимает английский на порту 3100, русский на
3101 (под `/ru/`) и проксирует `/ru` с английского сервера, чтобы
переключатель языка работал в обе стороны. Порты не пересекаются с
Django-Chassis (3000/3001), оба сайта можно держать одновременно. Если
нужно переключать языки, запускайте `docs:dev`, а не один `docs:dev:ru`.

```bash
npm run docs:typecheck
npm run docs:build
npm run docs:serve
```

## Бейджи версий

Любая новая публичная настройка, тип или extra должна быть помечена на
**обоих** языках:

```mdx
<Since v="1.1.0" />
```

Изменения поведения или сигнатуры — `<Changed v="..." />` и запись в
`CHANGELOG.md`. Версия бейджа — версия пакета, в которой фича впервые вышла.

## Соглашения проекта

- **Полная типизация** — аннотируйте параметры, возврат и переменные. Цель —
  `pyrefly` strict.
- **Без относительных импортов** — только абсолютные
  (`from django_gc.services import get_value`).
- **Именованные аргументы** — передавайте аргументы по имени, где возможно.
- **`uv run`** — команды Python как `uv run pytest`, не голый `python`.
- Runtime-код читает и пишет через `get_value()` / `set_value()`, не через ORM.
- Доменные ключи живут в проектном `StrEnum` и передаются в эти вызовы.
- Английская и русская документация остаются синхронными.
- Изменения публичного API требуют записи в `CHANGELOG.md`.

## CI, публикация и деплой

Push в любую ветку и pull request запускают проверки безопасности. При push в `main` сканирование и тесты отображаются в одном запуске CI. Тесты начинаются после успешного сканирования. Для остальных веток после успешного сканирования push тесты запускаются только для актуального коммита защищённой ветки. Тесты можно запустить вручную во вкладке **Actions**.

Тестовый workflow проверяет lock-файл и состояние миграций Django, прогоняет матрицу Python и Django, собирает wheel и sdist, а также проверяет и собирает обе языковые версии документации. Workflow безопасности проверяет секреты, Python, шаблоны Django, JavaScript и TypeScript документации и файлы GitHub Actions. Отдельно выполняется аудит закреплённых зависимостей Python и npm.

Релизный workflow сканирует коммит, сверяет его с текущей вершиной `main` и требует успешный запуск `testing.yml` для этого SHA в `main`. Дождитесь завершения тестов перед публикацией. Ручную публикацию запускайте из `main`. После загрузки wheel и sdist в PyPI запускается деплой документации для опубликованного коммита. Workflow документации проверяет принадлежность коммита ветке и использует результат уже пройденных тестов перед деплоем по SSH. Workflow документации получает секреты из `docs-production` и устанавливает файлы деплоя в домашний каталог SSH-пользователя. Self-hosted раннер Linux X64 собирает образ выбранного коммита и передаёт его по SSH. SSH-пользователь загружает готовый образ и запускает контейнер в существующей сети `docs_net` по адресу `DOCS_IP`. При ошибке проверки готовности скрипт восстанавливает прежний образ и порт.
